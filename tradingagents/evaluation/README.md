# 固定输入评估：第一阶段

当前阶段建立可重复的基线，不修改生产 Agent 的决策行为。后续依次增加证据关联、证据不足路由，再比较多轮讨论与模型分工。

## 数据集与评估边界

`fixtures/cases.v1.json` 包含 30 个合成诊断案例，每类 6 个：正常信息、数据缺失、来源冲突、数据过期、历史日期限制。公司、网址和数据均为虚构，适合检查具体失败模式，不代表真实金融研究任务的分布。

参考标注是项目作者制定的初始审核规则，尚未经过独立专家复核；没有买卖方向的标准答案。每个案例提供可确认事实、禁止推断、局限项、证据状态和是否应避免方向性结论。不要将其直接用于宣称投资准确率。

所有证据包含信息可用日期 `available_at` 与数据所属期间 `period_end`。回放先按可用日期过滤，不能因为财报期间结束就提前读取尚未发布的财报。包含未来信息的原始案例只供评估代码和审核人员读取，模型输入不含未来证据或参考标注。

## 不调用模型：验证评估流程

在项目目录执行：

```bash
.venv/bin/python -m tradingagents.evaluation.run
```

默认是 `smoke` 模式，30 个案例全部离线生成输入、报告占位和审核文件，不访问模型或市场数据服务，也不评估模型质量。输出位于 `eval_results/`，已从 Git 排除。`summary.json` 的 `quality_evaluated` 为 `false`，质量、模型延迟和成本指标为 `null`；不能把 smoke 运行成功率当成模型完成率。

## 调用现有分析图：取得真实模型基线

先在本机环境变量中配置服务商、有效模型 ID 和密钥。评估命令不会自动加载 `.env`，可通过 IDE 的环境变量配置或终端当前会话配置；不要把密钥写入命令历史或发给别人。

```bash
.venv/bin/python -m tradingagents.evaluation.run \
  --mode model --allow-model-calls --case missing-01 --repeat 1
```

此模式**会调用模型，可能产生费用**。必须明确指定 `--allow-model-calls`，并用 `--case` 或 `--limit` 限定范围，先检查单案例输出再扩大。一个案例会运行整个多 Agent 图，可能包含多次模型调用。Ctrl+C 可以中止，已完成案例的汇总会逐个保存。

评估沿用现有角色、提示词、结构化输出和讨论轮数，通过评估专用作用域替换数据工具和情绪分析预取数据，并注入冻结的标的身份；禁用历史记忆和检查点复用。上下文中的参考事实和禁止推断不会进入提示词。运行时不得与 Web 服务放在同一个 Python 进程：工具替换是进程级的；请独立执行本模块。

**这是按工具领域回放证据包，不是对第三方 API 原始响应的逐字录制。** 指标数值是案例提供的已知输入，不评估真实行情适配器或指标计算的正确性；错误标的、未来日期和未记录数据源不会回退到联网查询。工具参数与返回证据均保存在 trace 中供复核。

每次运行保存：

- `manifest.json`：数据集版本与 SHA-256、代码和提示词源码指纹、Git 提交（如有）、Python 与关键依赖版本、模型及讨论配置。
- 各案例目录：模型可见的 `input.json`、审核用的 `reference.json`、最终 `state.json`、Markdown 报告、`trace.json` 和执行结果。
- `runs.json`：执行状态、端到端耗时、模型调用、Token 与工具调用数量。
- `reviews.json`：待填写的人工审核表。
- `summary.json`：执行统计及人工审核后的质量指标。

同一配置可使用 `--repeat 3` 观察波动。Token 统计依赖服务商返回的 usage；缺失会显式标记，不能把缺失当作零费用。

可通过 `--input-usd-per-million` 和 `--output-usd-per-million` 指定价格估算成本，仅在 usage 完整且两个价格均提供时计算。当前是**统一 Token 单价的粗略估算**，不同模型、缓存计费及推理 Token 的实际账单可能不同；精确分模型成本留待后续阶段。

## 人工审核与指标

打开案例报告，对照 `reference.json` 和输入证据，填写 `reviews.json`：

1. 设置 `reviewer` 和 `reviewed: true`。
2. 将可验证的事实断言拆为原子结论，填写 `claim_count` 和有充分支持的 `supported_claim_count`。意见、建议、重复表达不重复计数。
3. 填写 `citation_count` 和 `correct_citation_count`。只有来源存在、时间合规且确实支持相邻结论才算正确；没有引用填 0，不得默认满分。
4. 对照参考事实填写 `covered_fact_count`。不要修改预填的 `reference_fact_count` 或 `expected_insufficient`。
5. `predicted_insufficient` 表示报告是否明确识别了整体或关键领域的证据不足；`unjustified_direction` 表示是否在缺乏充分依据时仍给出无保留的方向性结论。特别注意 Hold 不能自动算作识别证据不足。
6. 在 `notes` 写下无依据断言、错误引用与未识别局限的具体例子。建议第二位审核人复核一部分样本；当前代码不自动解决标注分歧。

然后重新汇总：

```bash
.venv/bin/python -m tradingagents.evaluation.run --review eval_results/对应运行目录
```

支持率、引用正确率和事实覆盖率按审核计数进行微平均；证据不足识别计算 precision / recall。分母为零时返回 `null`，不强行置为 0 或 1。没有完成审核时不生成质量评分，smoke 结果和失败运行不能充当质量样本。P50/P95 仅统计成功的真实模型运行耗时，完成率单独展示，避免隐藏执行失败。

## 下一步

1. 先复核首批合成参考标注，使用少量真实模型案例取得基线。
2. 为生产工具引入统一证据对象，让关键结论关联证据 ID。
3. 实现证据不足补查、停止和“无法判断”的显式状态。
4. 扩充真实历史快照与独立审核，再比较单 Agent / 多 Agent / 不同讨论轮数。当前尚未完成这些能力，也没有发布真实模型质量结论。
